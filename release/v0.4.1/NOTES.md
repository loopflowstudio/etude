# v0.4.1

<!-- loopflow:release-notes=narrative;gate=safe -->

Etude v0.4.1 brings training and evaluation into one experiment file, so another launch submits outstanding work against stored results and the existing queue. Evaluations can share a machine, compare policies across experiments and grow their game counts without replaying completed seed indices. This release also replaces version-specific launcher databases with explicit upgrades of one shared database and keeps capacity refusals from consuming queued runs' attempt budgets. These notes cover changes since v0.4.0. ([#113](https://github.com/loopflowstudio/etude/pull/113), [#114](https://github.com/loopflowstudio/etude/pull/114), [#115](https://github.com/loopflowstudio/etude/pull/115), [#117](https://github.com/loopflowstudio/etude/pull/117), [#119](https://github.com/loopflowstudio/etude/pull/119), [#120](https://github.com/loopflowstudio/etude/pull/120))

## Advance an experiment from one file

Training stages and evaluations no longer need separate launch bookkeeping. Declarations read experiment state to introduce later work, while each launch compares those declarations with delivered results and queued runs. ([#113](https://github.com/loopflowstudio/etude/pull/113))

- Declare named `TrainingJob`s in `training_jobs()` and tournament-based `EvalJob`s in `eval_jobs(state)`. `etude launch FILE` and `etude queue FILE` submit outstanding training and matches, reporting existing work, failures and budget holds. Each invocation makes one pass; discovering later stages requires another invocation. `etude train` and `etude eval` run the respective work locally. ([#113](https://github.com/loopflowstudio/etude/pull/113))
- Declared training addresses always use `EXPERIMENT/JOB@SEED`, so adding jobs or seeds does not rename existing runs. Stored compact addresses remain readable and are matched by their recorded job name and seed. ([#113](https://github.com/loopflowstudio/etude/pull/113))
- Pass generated files between stages with selections such as `state.run("player@0").out.matching("packs/*.pack").inputs("source")`. Selections use published output membership without downloading file contents; consumers receive verified files through `run.input("source")`. Inputs do not become the consumer's outputs. Prefer finished producers or immutable files: replacement before delivery causes `input_undelivered`, and widening a selection requires a new consumer job name rather than automatically retraining an existing job. ([#116](https://github.com/loopflowstudio/etude/pull/116))
- Continuations reuse retained source archives, so losing the submitting checkout does not prevent continuation. Remote administration runs the existing CLI over SSH. ([#119](https://github.com/loopflowstudio/etude/pull/119))

## Compare more policies without repeating completed games

Evaluations can select another experiment's policies directly and run compatible tournaments together. Etude owns checkpoint loading and inference batching; game code retains actions and randomness. ([#115](https://github.com/loopflowstudio/etude/pull/115), [#117](https://github.com/loopflowstudio/etude/pull/117))

- `PolicyKey` identifies a policy by experiment, job, seed and role; `state.policy(key).checkpoints` selects published checkpoints across continuations. Publish a separately selectable role with `run.checkpoint(..., role="exploiter")`. Experiment and role distinguish checkpoint identities and report curves. A named selection without a seed selects every seed; a policy key defaults to the lowest seed. ([#115](https://github.com/loopflowstudio/etude/pull/115))
- Compatible eval jobs share one run and machine slot, deduplicate checkpoint inputs and combine job limits. Pending matches can be submitted within budget without waiting for training to finish or for an estimated minimum amount of evaluation work. ([#117](https://github.com/loopflowstudio/etude/pull/117))
- `Agents(load=load, build=build)` separates deterministic checkpoint forwards from composed players and game logic. GPU games share batches across tournaments; CPU games cache and call forwards directly. Composed player settings distinguish player identities while checkpoint leaves reuse loading. Visible NVIDIA hardware selects shared batching, but the loader still chooses the model device; GPU residency is not guaranteed. ([#117](https://github.com/loopflowstudio/etude/pull/117))
- Completed matches are offered to storage individually. Infrastructure interruptions leave unfinished matches eligible for automatic retry; ordinary game errors stop the affected tournament while others continue. Delivered matches are skipped within the experiment's results. ([#117](https://github.com/loopflowstudio/etude/pull/117))
- Indexed matches derive seeds from the base seed and index, independently of players and seat order. Increasing `games` preserves completed match keys, and workers receive the selected matches rather than selecting them again. Switching an existing config-panel tournament to indexed matches requires a fresh tournament name. ([#119](https://github.com/loopflowstudio/etude/pull/119))

## Keep capacity available for the next run

Provider refusals previously could exhaust attempts before any code ran, and finished work could leave a rental blocking the next launch. Queued work now preserves its attempts through definite refusals, and waiting includes requested rental shutdowns. ([#120](https://github.com/loopflowstudio/etude/pull/120))

- RunPod create refusals report a sanitized provider reason and release capacity. Queued work retries no sooner than 60 seconds later without spending attempts. Uncertain create replies still require reconciliation. ([#120](https://github.com/loopflowstudio/etude/pull/120))
- `etude wait` confirms requested rental shutdowns and collects final logs before returning. Rentals explicitly kept do not hold it open. ([#120](https://github.com/loopflowstudio/etude/pull/120))
- Pools and on-demand capacity replace cohorts. `--max-usd` limits admission using completed costs and queued or running jobs' dollar limits; this experiment limit applies only to the current pass and is not retained. ([#113](https://github.com/loopflowstudio/etude/pull/113))
- Persistent refusals can leave a queue waiting indefinitely, including for authentication failures: create responses in the 4xx range except 408 are treated as refusals, including 401 and 403. Advancing the queue requires `wait` or another scheduling loop. ([#120](https://github.com/loopflowstudio/etude/pull/120))

## Operational notes

**Upgrade the launcher database explicitly.** The final database is `launcher.sqlite`, superseding both v0.4.0's versioned-file policy and the earlier `launcher-20.db` change in this cycle. Compatible clients share this file. `etude database status` checks local schema compatibility without credentials or network access; `etude database upgrade` initializes or advances it. Ordinary commands never migrate, and a server's database must be upgraded on that server. ([#113](https://github.com/loopflowstudio/etude/pull/113), [#114](https://github.com/loopflowstudio/etude/pull/114))

- **Legacy launcher files are not automatically consolidated.** Their one-time conversion remains separate operational work: stop local scheduling, preserve and reconcile existing facts, update relevant environments and retire old active filenames while workers and deadline guardians continue. The shared-database API does not import those legacy queues for you. ([#114](https://github.com/loopflowstudio/etude/pull/114))
- **Upgrades retain snapshots and apply SQL transactionally.** Incompatible writers and scheduling passes stop before further actions. Managed servers hand over to a validated installed program or report that a restart is required. In-flight requests may still complete during an incompatible upgrade; both those requests and any snapshot restoration require reconciliation with live provider state. ([#114](https://github.com/loopflowstudio/etude/pull/114))
- **Update declarations, commands and imports.** Use the unified training/eval declarations above. `etude controller` becomes `etude server`; set an existing server selection again. Supported Python names live in their defining modules, and replaced paths have no forwarding aliases. Training uses `track(config=...)` inside a run assigned by `etude train` or the launcher. ([#113](https://github.com/loopflowstudio/etude/pull/113), [#119](https://github.com/loopflowstudio/etude/pull/119))
- **Update evaluation code to the final API.** Games use `play(match, agents)` and checkpoint seats use `CheckpointSlot()` and `checkpoint_player(ref)`. Remove `workers=` and `--min-eval-hours`. Eval jobs belong to their file's experiment: replace `EvalJob(experiment=...)` with seat selectors or checkpoints read through `observe`. Construct checkpoint references with flat policy fields or `PolicyKey.checkpoint(...)`; outside checkpoints use `address=`. ([#115](https://github.com/loopflowstudio/etude/pull/115), [#117](https://github.com/loopflowstudio/etude/pull/117), [#119](https://github.com/loopflowstudio/etude/pull/119))
- **Stored results remain readable.** The retained stats database rebuilds once; queries that match checkpoint keys literally must account for the experiment prefix. Historical cross-experiment references without provenance are interpreted as belonging to the evaluating experiment. Each experiment schedules from its own delivered results, so matches delivered elsewhere can be played again. Smoke marks cross-experiment seats `not smoked` because its temporary store contains only the current file's runs. Released records and queued evaluations remain readable through the later API reorganization. ([#115](https://github.com/loopflowstudio/etude/pull/115), [#119](https://github.com/loopflowstudio/etude/pull/119))
- **Contributor migration rules are enforced.** Named SQL migrations carry checksums and minimum reader versions; merged migrations are immutable. Packaged merge evidence permits operational upgrades before release, while unmerged SQL is restricted to empty development fixtures. ([#114](https://github.com/loopflowstudio/etude/pull/114))

## Small changes

- `etude fetch` retrieves published `run.out` files and attempt outputs, verifies fingerprints and lists available names when a requested output is absent. Storage failures produce a one-line CLI error. ([#120](https://github.com/loopflowstudio/etude/pull/120))
- Short author guides and `examples/prototype.py` demonstrate training, evaluation and reporting with a learned coin-bias predictor and a fair-coin baseline. Architecture and persistence references live under `docs/dev/`. ([#119](https://github.com/loopflowstudio/etude/pull/119))
- Evaluation protocol reports retain play intervals and inference costs for inspecting concurrency and overhead. ([#117](https://github.com/loopflowstudio/etude/pull/117))
- Index-refresh regression coverage uses storage counts instead of a flaky process-wide memory peak threshold. It still checks bounded writes, no storage reads during publication, unchanged permanent history and correct latest values; it no longer checks peak memory use. ([#118](https://github.com/loopflowstudio/etude/pull/118))
